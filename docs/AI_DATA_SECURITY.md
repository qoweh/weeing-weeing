# AI 사용 시 데이터 외부 반출 관리

외부 AI API(LLM·임베딩·리랭크)를 쓰면 설비 데이터와 문서가 회사 밖으로 나간다. 기업은 이 문제를 보통 어떻게 관리하는지, 이 프로젝트는 지금 어디까지 했는지, 실제 공장 데이터를 넣기 전에 무엇을 해야 하는지 정리한다.

- 지금 단계는 캡스톤 시연이다. 넣는 데이터는 가상 공정의 시뮬레이터 값과 팀이 만든 문서다. "외부 반출 금지"는 **나중에 검토**하기로 했다(2026-11-03). 이 문서는 그때 쓸 기준이다.
- 법률 자문이 아니다. 실제 도입 때는 회사 보안·법무 담당과 확인한다.
- 공급자 정책은 **2026-11-03 공식 문서 기준**이다. 정책은 자주 바뀌므로 도입 시점에 다시 확인한다.

## 1. 지금 무엇이 어디로 나가는가

| 보내는 곳 | 언제 | 보내는 내용 | 설정 |
|---|---|---|---|
| Anthropic Claude API | 사건 분석, 챗봇 질문 | 사건 정보(룰 코드·센서 값·시각), 검색된 문서 조각, 챗봇 질문·대화 일부 | `ANTHROPIC_API_KEY`. 사번·결재 정보는 보내지 않는다(`agent/analyst.py`) |
| Langfuse(팀 EC2 서버, 자체 호스팅) | LLM 호출마다 | 기본으로 프롬프트·응답 본문까지 | `LANGFUSE_CAPTURE_CONTENT=false`면 토큰·모델·시간만 |
| Voyage AI(MongoDB) | **켰을 때만**. 기본은 꺼짐 | 문서 등록 때 **문서 본문 전체**, 검색 때 질의문, 리랭크 때 후보 조각 | `EMBEDDING_PROVIDER=voyage`, `RERANKER_MODEL` |
| (외부로 안 나감) | 기본 임베딩·키워드 검색 | 해시 임베딩·Kiwi BM25는 서버 안에서 계산 | `EMBEDDING_PROVIDER=hashing` |

임베딩 API를 켜면 원문이 통째로 나간다는 점이 LLM 호출과 다르다. LLM은 검색된 조각 몇 개만 받지만, 임베딩은 색인할 때 모든 문서를 받는다.

## 2. 기업이 보통 하는 관리

### 2-1. 기준 문서와 규정

| 구분 | 내용 | 이 프로젝트와의 관계 |
|---|---|---|
| 국가정보원 「AI 보안 가이드북」(2025-12-10 배포) | 2023년 「챗GPT 등 생성형 AI 활용 보안 가이드라인」 개정. 생성형·에이전틱·피지컬 AI의 15개 보안 위협, 30개 대책, 수명주기별 57개 점검 항목. ChatGPT·Claude·Gemini 보안 설정 포함. 공공기관 대상이지만 민간도 참고 | 점검표로 쓰기 좋다. 국가기관은 행정망 안에 AI 모델을 자체 구축해야 한다는 국정원 관계자 발언이 보도된 적이 있다(시점 미확인) |
| OWASP Top 10 for LLM Applications 2025 | LLM02 민감정보 노출, **LLM08 벡터·임베딩 약점**(RAG 접근 통제 실패, 임베딩에서 원문 추정, 데이터 오염) | 우리 RAG 구조에 바로 해당 |
| NIST AI RMF, ISO/IEC 42001 | AI 위험관리 체계·AI 경영시스템 국제 표준 | 회사 차원의 관리 체계. 국정원 가이드북도 참고했다 |
| 개인정보보호법 | 개인정보를 국외로 보내면 국외 이전 요건(제28조의8)을 따라야 한다. 개인정보위는 「생성형 AI 개발·활용을 위한 개인정보 처리 안내서」(2025-08-06)를 냈다 | 작업자 이름·사번 같은 개인정보를 프롬프트에 넣지 않으면 피할 수 있다 |
| 산업기술보호법 | 국가핵심기술은 수출(국외 이전)에 정부 승인·신고가 필요하다(제11조) | 배터리 공정 기술이 해당될 수 있다. 실제 공정 문서를 해외 API에 보내기 전에 회사가 판단해야 한다 |
| 부정경쟁방지법(영업비밀) | 영업비밀로 보호받으려면 "합리적인 노력으로 비밀로 유지"해야 한다 | 통제 없이 외부 AI에 넣으면 나중에 비밀관리성을 다투기 어려워질 수 있다 |
| 방송통신위원회 「생성형 AI 서비스 이용자 보호 가이드라인」(2025-02-28) | AI 서비스 제공자 대상. 입력 데이터의 학습 활용 고지·거부 절차 등 | 우리가 외부에 서비스를 열 때 해당. 내부 도구인 지금은 참고만 |

### 2-2. 흔히 쓰는 통제 (약한 것 → 강한 것)

1. **사용 정책과 데이터 등급.** 데이터를 공개·내부·기밀·개인정보로 나누고, 등급별로 보낼 수 있는 곳을 정한다. 승인된 공급자 목록(allowlist)과 책임자를 둔다.
2. **계약 확인.** 공급자 약관과 데이터 처리 계약(DPA)에서 다음을 확인한다.
   - 학습에 쓰는지. 예: Anthropic은 상용 API 데이터를 명시적 허락 없이 학습에 쓰지 않는다고 밝힌다. Google Gemini 무료 티어는 제품 개선에 쓴다. MongoDB(Voyage)는 Atlas 조직 설정에서 모델 개선용 수집을 관리한다
   - 얼마나 보관하는지, 무보관(ZDR) 계약이 되는지. Anthropic은 ZDR을 신청받아 조직 단위로 적용한다(일부 기능은 제외)
   - 어느 나라에서 처리하는지(data residency). Anthropic API는 `inference_geo`로 처리 지역을 지정하는 기능이 있다
3. **최소 전송.** 필요한 필드만 보낸다. 이름·사번·연락처 같은 식별자는 보내기 전에 지우거나 가명으로 바꾼다(마스킹). 이 프로젝트는 사건 정보에 사번을 넣지 않는다.
4. **키·로그 관리.** 키는 비밀 관리 도구에 두고 환경마다 나누며 주기적으로 바꾼다. 사용량 상한을 건다. 관측 도구(Langfuse 등)에 본문을 남기면 그곳도 같은 등급으로 보호한다.
5. **송신 통제.** 외부로 나가는 요청을 한 게이트웨이(프록시)로 모아 허용된 주소만 통과시키고 기록한다. 민감정보 탐지(DLP)를 붙이기도 한다.
6. **벡터 DB도 원문처럼 보호.** 임베딩에서 원문을 일부 추정할 수 있다(OWASP LLM08). 검색 결과는 사용자 권한·문서 상태에 맞게 거른다(우리는 `status=approved`·문서 버전 확인).
7. **배치 위치를 안쪽으로.** 위험이 클수록 다음 순서로 옮긴다.
   공개 API → 자기 클라우드 계정·리전 안의 관리형 서비스(예: AWS Bedrock) → 전용·VPC 배포 → 사내(온프레미스)·오픈 가중치 모델.
   안쪽일수록 데이터 통제는 강해지지만 비용·운영 부담이 커진다. 이 프로젝트는 서버 자원 때문에 로컬 모델을 뺐다(D-31).

## 3. 실제 데이터를 넣기 전 점검표

- [ ] 보낼 데이터의 등급을 정했다(공정 조건·도면·정비 이력이 기밀인지, 국가핵심기술 해당 여부)
- [ ] 공급자별로 학습 미사용·보관 기간·처리 지역을 확인하고 기록했다
- [ ] Voyage를 켠다면 Atlas 조직 설정에서 모델 개선용 데이터 수집을 껐다
- [ ] 필요하면 Anthropic ZDR을 신청했다
- [ ] 운영 환경은 `LANGFUSE_CAPTURE_CONTENT=false`로 본문을 남기지 않거나, Langfuse 서버를 같은 등급으로 보호한다
- [ ] 프롬프트에 개인정보가 들어가지 않는지 확인했다(사번·이름·연락처)
- [ ] API 키를 서버 비밀값으로만 두고, 사용량 상한과 알림을 걸었다
- [ ] 외부 반출이 안 되는 등급의 데이터는 `EMBEDDING_PROVIDER=hashing` + 리랭커 끔으로 두거나, 사내 배치 모델을 다시 검토한다
