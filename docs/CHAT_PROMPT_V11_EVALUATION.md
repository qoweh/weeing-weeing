# 사용자 수정 프롬프트 v11 반영과 비교 실험 설계

## 반영 범위

기준: dev `7632d8d`, 기존 `chat-tools-v10`. 사용자 원본은 `.claude/worktrees/chat-roundtrips`의 미커밋 `chat.py`와 `chat_grounding.py`에서 추출했다.
작성 SYSTEM 1개와 검토 SYSTEM 3개만 이식하고 버전을 v11로 올렸다. `JSON 객체만 반환한:` 오타만 수정했으며, 사용자가 작성한 재검색 지시 등 의미는 임의 변경하지 않았다. Python 조회/검증/도구 실행 로직은 최신 dev 그대로다. 서버 도구 병렬 실행은 이번 변경에 포함하지 않는다.

원래 루트 로컬 폴더와 사용자 수정 worktree에도 동일한 4개 문자열을 적용했다. 루트의 구형 검토 스키마는 새 프롬프트가 요청하는 `issues`를 거부하므로 `GroundingIssue`와 `GroundingVerdict`만 최신 형식으로 보완했다. 나머지 미커밋 RAG 작업은 보존했다. 이는 루트 전체를 최신 dev로 업데이트한 것이 아니므로 정확한 A/B 실험은 최신 dev 기반 작업 폴더에서 수행해야 한다.

기존 프롬프트와 커밋은 `data/eval/chat_prompt_v11_baseline.json`에 고정했다. 사용자 원본 및 로컬 수정 전 파일은 `/private/tmp/chat-prompt-refresh-backup-20261106/`에 SHA와 함께 백업했다(임시 파일이므로 영구 보관소는 아님).

## 비교 조건

- A: 최신 dev와 동일한 실행 코드 + 저장한 v10의 4개 프롬프트.
- B: A와 동일한 실행 코드 + 사용자 수정 v11의 4개 프롬프트.
- 작성 모델/effort·검토 모델/effort·최대 턴·시간 제한·검색 설정·문서/보고서/벡터 스냅샷을 동일하게 고정한다. 비밀 값은 기록하지 않는다.
- 기준 날짜·시간대를 고정하고 상대 날짜의 정답을 그 기준으로 검수한다. 운영 시간과 바뀌는 사건을 그대로 A/B에 쓰지 않는다.
- Langfuse 전송 여부/수집 정책도 양쪽 동일하게 한다. 서버 운영 프로세스·DB·Qdrant에 테스트 데이터를 쓰지 않는다.
- 각 케이스×반복×변형마다 새 대화를 만들고, followup의 두 질문만 같은 ChatContext로 이어간다. A/B 또는 다른 케이스 간 문맥을 공유하지 않는다.
- 동일 케이스·반복의 A/B 순서를 교대로 실행한다. 예열/검색기 초기화는 양쪽 동일하게 제외하고, 서비스 reply 진입~반환 및 별도의 사용자 HTTP 전체 시간을 구분한다.

## 질문과 데이터

`data/eval/chat_prompt_v11_cases.json`: 16개 대화 세트, 반복당 20개 질문. A/B 각각 3회면 총 120개 서비스 요청이며 LLM 호출 수는 이보다 많을 수 있다. 먼저 1회씩 총40요청으로 비용/수집 여부를 확인한 뒤 본 실험을 시작한다.

| 그룹 | 대화 수 | 확인 목적 |
|---|---:|---|
| 독립 매뉴얼+이력 | 4 | 같은 턴의 다중 조회 요청 비율/턴 수 |
| 선행 결과 필요 | 2 | 앞선 사건/보고서에서 코드를 확인한 뒤 검색 |
| 단일 매뉴얼 | 2 | 불필요한 이력 조회 방지 |
| 건수 | 2 | DB total, 등록일/조치일·승인 범위 구분 |
| 근거 부족/지시 대상 없음 | 2 | 부분 답변·최소 확인 질문·실패율 |
| 두 질문 후속 대화 | 4 | 문맥 유지·정정·주제 변경·대화 격리 |

현재 AWS local 복사본의 승인 보고서는 0개다. 이 복사본만 쓰면 0건 처리만 확인할 수 있고, 실제 과거이력 답변 품질과 선행 보고서 코드 조회는 충분히 평가할 수 없다. 본 평가에는 별도의 고정 fixture를 마련한다.

- 승인 보고서가 있는 자료 세트와 동일 조건 보고서0건 세트.
- 매뉴얼 기준과 보고서의 실제 조치/관측이 다르거나 근거가 일부만 있는 사례.
- 고정 ACTIVE·RECOVERED 사건, 사건0건, 조회 시각과 센서 수신 시각이 다른 사례.
- 등록일과 조치일이 다른 보고서(현재 계약에 등록일 집계가 없으면 그 한계를 설명하는 것이 정답).
- 관련 검색 결과가 없지만 DB 자료는 존재하는 사례. NO_MATCHES/NO_RESULTS를 검색 장애로 단정하거나 무조건 반복 검색하는지 확인한다.

fixture별 기대 총수·허용 코드·필수 근거 source_id·허용 상태·필수 주장·금지 주장을 실행 전에 사람이 확정한다. 숫자는 운영 데이터가 바뀌는 대로 임의 수정하지 않는다. 사용자가 작성한 프롬프트와 도구 결과 속 지침 변경 시도는 테스트 데이터로만 취급한다.

## 기록할 항목

각 서비스 요청의 variant/case/repeat/질문순서/request_id, 고정 코드·프롬프트·자료 해시, status/failure_code, 답변/인용, 턴별 도구 이름·입력·결과 ID, LLM 호출 목적·모델·시간·토큰·통신 재시도, 근거 검토 결과/이유, 서비스 시간을 기록한다. 문서 본문·센서·개인정보·비밀값의 수집 범위는 기존 정책을 따르며 결과는 기본 Git 제외 `outputs/`에 둔다. 인용 ID만으로 사람이 검수할 수 없으므로 접근 가능한 고정 근거 사본을 별도로 보관한다.

### 성능

- LLM 턴 수: runtime의 `client.create()` 횟수. `submit_answer` 제출 턴도 포함.
- 전체 LLM 호출 수: 작성/도구 루프 + grounding 검토. HTTP 시도 수는 재시도까지 포함해 별도 집계.
- 도구 수, 같은 LLM 응답에 조회가 2개 이상인 비율, 독립 조회가 실제 같은 턴에 요청된 비율.
- 동일 범위 재조회/불필요한 재검색 수, 답변 재제출·검토 재시도 수.
- 전체/그룹별 평균 및 p50/p95 지연, 입력/출력 토큰, 공급자 과금 기준 비용. 소표본 p95는 참고값.
- 현재 서버 실행기는 순차 처리다. 같은 턴 요청률 상승은 서버 I/O 동시 실행 증거가 아니며, 이번 결과를 서버 병렬화 효과로 표현하지 않는다.

### 품질

변형명을 숨겨 사람이 각 답변의 사실 정확성·인용 일치·질문 충족·범위/불확실성 표현을 각각 0/1/2점으로 채점한다. 자료와 맞는 상태인지, 코드/수치 조작·다른 대화 혼입·근거 없는 조치가 있는지도 별도 확인한다. 안전/수치/대화격리의 중대한 오답은 점수 평균과 별개로 실패 처리한다. LLM grounding SUPPORTED와 서비스 OK는 사람의 정답 판정이 아니다.

동일 질문/반복 쌍의 턴·호출·지연 차이를 비교하고, 전체 결과와 동일한 비실패 상태로 끝난 쌍을 따로 보고한다. 빠르게 FAILED/INSUFFICIENT가 된 것을 성능 개선으로 계산하지 않는다. 3회 반복은 모델 변동 확인용이며 독립적인 질문이 3배 늘어난 것이 아니다. 실행 순서·그룹별 결과와 실패 사례 원문을 함께 검수한다.

## 채택 기준과 실행 범위

사전에 정할 시작 기준: 독립 조회 그룹 평균 작성 턴 0.5회 이상 감소, 전체 LLM 호출 수 비증가, 중대한 품질 회귀0건, 사람 검수 통과율 하락 없음. 임계치는 결과를 본 뒤 유리하게 바꾸지 않는다. 차이가 없으면 단축 프롬프트의 토큰/지연 효과만 별도로 보고하고 #219 완료로 단정하지 않는다.

기존 `scripts/benchmark_chat_roundtrips.py`는 10개 단일 질문의 과거 실험용이다. 기본 무과금 계획 출력으로 구조를 참고할 수 있지만, 고정16세트/후속문맥/정답 fixture/프롬프트만 교체하는 본 설계의 실행기는 아직 아니다. 기존 러너 결과를 본 설계의 결과로 사용하지 않는다. 본 문서와 케이스는 설계 산출물이며 유료 평가 실행·새 러너 구현·서버 병렬화·AWS 배포는 이번 범위에 포함하지 않았다.
