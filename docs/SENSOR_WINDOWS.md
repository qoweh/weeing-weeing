# 사건 센서 구간 조회와 수치 검증 (#105)

## 처리 순서

1. 기존 #104 작업자가 Error 발생 당시 Incident 스냅샷으로 분석을 시작한다.
2. API가 `db.interface.get_telemetry()` 저장소로 만든 읽기 전용 `SensorReader`를
   `agent.interface.get_analyzer(..., sensor_reader=...)`에 주입한다. Agent는 DB를 import하지 않는다.
3. Claude가 필요할 때 `get_sensor_window`를 선택한다. 사건의 `last_detected_at`을 기준으로
   앞 0~120초, 뒤 0~30초와 센서 필드(최대 10개)를 지정한다. 설비·공정·사건 ID는 변경할 수 없다.
4. DB의 `[start,end)` 조회를 이용하되 요청 종료 표본을 포함하도록 끝에 1μs를 더한다.
   같은 공정·설비의 최신 저장 시각을 조회 시작 시 고정한다. 이후 표본을 기다리지 않는다.
5. 최대 512개 표본에서 선택 필드의 단위·유효/결측 수·처음/마지막 값, 숫자의
   min/max/mean/delta 또는 bool의 true/false 개수, 값이 달라진 **관측 시각**을 반환한다.
   변화 목록은 필드마다 최대 16개이며 초과 여부를 알린다. 원시 행 전체는 전송하지 않는다.
6. 모델은 제출 도구에 `sensor_claims`로 조회 ID·필드·통계·값을 제출한다.
   현재 실행에서 반환한 통계만 허용하며 bool과 숫자를 구별하고 절대 오차 0.000001 이내로 대조한다.
   틀린 값·조회하지 않은 필드·결측 통계는 도구 오류로 반환되어 기존 반복 상한 안에서 수정하게 한다.
7. 서버가 Incident 원본과 검증된 수치로 `observed_facts` 및 후보의 관측 `basis`를 작성한다.
   이 두 칸의 모델 자유 서술은 저장하지 않는다. 조회 한계는 `limitations`에 보존한다.
   기존 문서 근거 ID·OK/INSUFFICIENT_EVIDENCE 검사 및 AnalysisResult 저장 계약은 유지한다.

## 관측 한계와 범위

- 표본은 각 행에 저장된 송신자 선언 주기를 기준으로 본다. 모두 같은 주기를 선언했다면
  그 주기의 1.5배 초과 간격을 표시한다. 주기 미제공/혼합 시 고정 0.5초를 가정하지 않는다.
  시작/종료 표본 부족·아직 미수집인 후속 구간·빈 조회·512개 초과도 표시한다. 간격 기준은 관측 품질 주의용이며
  룰의 지속시간 판정을 새로 수행하지 않는다. 중간 누락 개수나 물리적 연속 점유 시간을 추정하지 않는다.
- None/NaN/무한대는 결측으로 집계하며 0으로 대체하지 않는다. 온도 등 결측 표본은 평균에서 제외한다.
- 변화 시각은 직전 유효 표본과 값이 달라진 시각이다. 그 사이의 실제 전환 순간을 뜻하지 않는다.
- source/run 식별자가 DB 계약에 없으므로 같은 공정·설비·시각의 별도 재생 실행은 구별할 수 없다.
  재현 시 별도 테스트 DB나 다른 설비 ID를 사용한다.
- 구조화 수치 검증은 전체 자유 서술의 의미 검증이 아니다. 원인 가설·점검/조치 문장 전체의
  사실성을 자동 보증하지 않으며 문서 근거 확인과 사람의 검토가 필요하다.
- `TelemetryProvenance`와 nullable telemetry.provenance JSON(0012)에 출처·주기를 별도 저장한다.
  15필드 입력·Unreal·PLC 동작은 유지하며 과거 행은 UNKNOWN으로 취급한다.
- quality에 요청/반환 범위, 미관측 구간 길이, 출처별 표본 수를 담는다. max_gap_seconds는
  반환된 표본 사이의 간격이다. 요청 전체의 연속 상태·수집률로 해석하지 않는다.
- `window-1` 등은 해당 분석 안의 참조이며 전역 ID가 아니다. 멀티 분석에서는 공개 단계 기록과
  재시도 체크포인트에 통계·관측 한계를 보존하며 원시 행·내부 대화는 포함하지 않는다.

## 터미널 확인

무료 오프라인 시연(서버·Docker·Unreal·API 키 필요 없음):

```powershell
$env:PYTHONPATH="src"
uv run --no-sync python scripts/demo_sensor_window.py
```

합성 표본 3개 조회 → rpm 평균 9999 제출 거절 → 1200으로 수정 → 최종 관측을 표시한다.
정비 근거 검색을 생략하는 시연이므로 최종 상태는 INSUFFICIENT_EVIDENCE다.

실제 자동 분석에서는 기존 서버의 `[분석 시작]` 다음에 모델이 조회를 선택하면
`[센서 구간 조회]`, `[센서 수치 검증 거절]`(불일치가 있을 때),
`[센서 수치 검증 완료]`, `[분석 저장 완료]`를 확인한다. 모델이 조회를 선택하지 않으면
조회 로그가 없고 사건 원본만으로 관측을 작성한다. 서버 재시작 뒤 새 Error 사건부터 적용된다.
기존 완료 작업은 자동 재분석하지 않는다.

독립 스크립트에서 실제 DB 조회 도구를 추가할 때(Claude API 비용 발생):

```powershell
$env:PYTHONPATH="src"
uv run --no-sync --env-file .env python scripts/analyze_incident.py --incident 사건.json --sensor-window
```

기본 예시 사건의 날짜와 DB 수집 날짜가 다르면 빈 조회가 정상이다. 실제 사건 JSON을 사용한다.
로컬 Qdrant를 사용하는 서버와 독립 분석 스크립트는 동시에 실행하지 않는다.
