# 챗봇 평가 방법과 계측

조회 범위·건수 전용 종료·본문 중복 제거·재작성 감소의 구현 설명은
[CHATBOT](CHATBOT.md)에 모았다. 이 문서는 평가 방법을 설명하며,
[과거 왕복 실측](CHAT_ROUNDTRIP_RESULTS.md)을 현재 v13의 재측정 결과로 취급하지 않는다.
실제 유료 실행은 사용자가 자기 터미널에서 수행한다. 자동 검증은 가짜 클라이언트를 쓴다.

## 프롬프트 A/B: 5문항·10요청

AWS local 기능이 있는 원래 로컬 저장소에서 실행한다. 실제 `.env`는 로드하지 않는다.

```bash
# 저장소 루트의 사용자 터미널에서 실행
# 기본은 무과금 계획 확인. 키 입력·Docker·DB·모델 호출 없음
make chat-prompt-eval

# AWS 자료가 바뀌었으면 먼저 검색용 복사본 동기화 및 검증
make aws-local ARGS='sync'
make aws-local ARGS='verify'

# 사용자가 터미널에서 직접 실행. Claude·Voyage API 비용 발생
make chat-prompt-eval ARGS='--execute --ask-key --ask-voyage-key'
```

키는 터미널 숨김 입력으로만 받는다. IDE의 열린 파일은 자동 문맥에 포함될 수 있으므로 키를 파일·채팅에 넣지 않는다. 실험 실행기는 기존 `scripts/aws_local.py`의 격리 프로필을 사용한다. 실행기/자료가 없는 새 clone에서는 먼저 해당 로컬 프로필을 구성해야 하며, 운영 DB 설정으로 조용히 대체하지 않는다. Docker만 켜는 것은 AWS DB 복사가 아니다.

기본5문항×기존v10/수정v13 각1회=서비스 요청10개다. 반복 실행 모드는 없다. 내부 작성·도구선택·근거 검토·통신 재시도는 요청당 여러 번 발생할 수 있어 LLM 호출10회라는 뜻은 아니다. 인증·한도·검색 장애 발생 시 추가 비용을 막기 위해 중단하며 부분 결과를 저장한다.

## 질문과 비교 조건

`data/eval/chat_prompt_v11_cases.json`의 다섯 질문을 사용한다.

| 질문 유형 | 질문 |
|---|---|
| 매뉴얼 | RPM 저하 시 조치 방법 알려줘. |
| 매뉴얼+이력 | 모터 외함 온도 기준과 과거 과열 조치 이력을 알려줘. |
| 정확한 건수 | 2026년 11월에 정비 조치가 있는 승인 보고서는 몇 건이야? |
| 근거 부족/부분답변 | 이 설비의 베어링 부품번호와 현재 교체 부품 재고 수량을 알려줘. |
| 선행 결과 필요 | 가장 최근 승인 정비 보고서의 고장 코드를 확인한 뒤 그 코드의 점검 기준을 찾아줘. |

A는 `chat_prompt_v11_baseline.json`의 기존v10 프롬프트4개이고, B는 현재 코드의 v13 프롬프트4개다. 실행기는 프롬프트와 버전만 메모리에서 바꾸고 종료 시 복원한다. 코드 파일·운영 데이터·검색 자료는 수정하지 않는다. 코드·조회기·모델/effort·시간예산·검색 설정은 양쪽 동일하며 같은 케이스의 순서는 AB/BA로 교대한다. 매번 새 ChatContext와 클라이언트를 사용한다. 이번 소규모 실험에는 후속대화가 없으며 질문 간 문맥을 섞지 않는다.

기존 로컬 프로필은 최신 dev와 런타임 코드 버전이 다를 수 있다. 기록한 실제 실행 소스 해시가 비교 기준이다. 동일 로컬 코드에서 프롬프트만 비교한 결과를 최신 AWS 코드의 결과라고 표현하지 않는다. Langfuse는 기존 AWS local 프로필 설정을 따르며 기본 비활성이다. 초기 검색기 준비 시간은 별도로 기록하고 본 요청 지연에서 제외한다.

## 산출물과 검수

기본 출력: Git 제외 `outputs/chat_prompt_eval/<시각>/`. `--output <새폴더>`로 지정할 수 있으며 기존 폴더는 덮어쓰지 않는다.

- `results.jsonl`: 요청별 원문 질문·답변·인용, 상태, 작성 턴/LLM호출/HTTP시도/검토 호출, 턴별 도구 목록, 지연·토큰·검토 기록. 토큰 미확인을0으로 채우지 않는다.
- `summary.json`, `comparison.md`: A/B 집계와 질문별 차이, 같은 비실패 상태 쌍 비교. 실패가 빨라진 것을 개선으로 계산하지 않는다.
- `prompts.json`: 실제 사용한 두 변형의 프롬프트 전체.
- `metadata.json`: 검색 자료 체크섬·변경 여부, 실행 소스 체크섬, 비밀 값 제외 모델/검색 설정.
- `quality_review.json`: 사람이 채울 정확성·인용·질문 충족·범위 표현 각0/1/2점, 중대한 오류 여부와 메모. 자동으로 품질 합격을 생성하지 않는다.

전체LLM호출은 도구 루프+근거 검토이고, 작성턴은 dialogue 목적 호출 수다. HTTP시도에는 재시도도 포함한다. 같은 턴에 독립 조회가 묶인 비율과 재검색 여부는 `turn_tools`를 케이스의 기대 동작과 대조한다. 현재 서버 도구 실행기는 순차다. 같은 턴의 다중조회가 실제 서버 병렬 실행이라는 뜻은 아니다.

현재 복사본에 승인 보고서가0개라면0건 처리만 평가할 수 있고, 실제 이력 답변/선행 보고서 코드 조회 품질은 평가 불충분으로 표시한다. 승인 보고서가 있는 고정 자료로 별도 확인이 필요하다. 등록일과 조치일·승인 범위도 혼동하지 않는다. source의 total, 수치·코드·인용이 실제 고정 근거와 맞는지 확인한다.

5문항1회는 초기 점검이다. 평균/질문별 차이·실패·재작성 감소를 살피되 통계적으로 검증된 개선이나 품질 비열등성을 주장하지 않는다. OK/SUPPORTED는 사람의 사실 검수를 대신하지 않는다. 결과에는 답변 본문이 포함되므로 외부 공유 전 개인정보와 운영 내용을 검토한다.

## 자동 검증과 실제 실행 범위

자동 검사는 가짜 클라이언트로 A/B 격리·10요청 상한·실패중단·버전/프롬프트 복원·산출물·Make 인자 전달을 검증한다. 실제 유료API 평가는 사용자가 명시적으로 `--execute`를 실행할 때만 한다. 서버 병렬화나 AWS 배포는 이 실험 코드의 범위가 아니다.

## 저장소만 받은 환경의 실행

AWS local 복사본 도구는 현재 로컬 개발 프로필의 별도 기능이며 이 PR에서 Qdrant 복제·재색인 코드를 배포하지 않는다. 해당 도구가 없는 새 clone은 명시적인 `--backend app`으로 현재 셸에서 설정한 애플리케이션의 DB·검색 저장소를 사용한다. `.env`는 자동으로 읽지 않으며 연결 설정은 사용자가 직접 준비한다. 복제 프로필로 조용히 대체하지 않는다.

```bash
make chat-prompt-eval ARGS='--execute --backend app --ask-key --ask-voyage-key'
```

이 모드는 현재 등록 문서/승인 보고서의 체크섬을 전후 비교해 데이터 변경 여부를 기록한다. 고정 시점 복제나 벡터 불변성을 보장하지 않으므로 평가 동안 업로드·재색인·보고서 갱신을 피하고, 변경 감지 시 비교 결과를 채택하지 않는다. 쓰기·재색인은 실행하지 않는다. 두 모드 모두 한 프로세스의 현재 CLI 클라이언트를 작성과 검토에 공유하며, 실제 호출 모델은 각 결과의 usage에 기록된다.


## 왕복 비교: 10문항·40요청

```bash
# 기본은 계획만 출력하며 SSH/실제 모델을 호출하지 않는다.
uv run --no-env-file --no-sync python scripts/benchmark_chat_roundtrips.py

# 실제 Claude·Voyage 비용 발생. 기존 SSH 별칭/서버 실행 설정 사용.
uv run --no-env-file --no-sync python scripts/benchmark_chat_roundtrips.py \
  --execute --repeats 2 \
  --output outputs/chat_roundtrips/comparison.jsonl
```

고정 10문항을 두 버전으로 각 2회 실행하므로 서비스 요청은 40회다.
`--repeats`는 1~5이며 기본 2다. 같은 출력 파일은 덮어쓰지 않는다.
각 질문의 기존/후보 실행 순서를 교대로 바꿔 한쪽이 항상 먼저 실행되는 편향을 줄인다.

후보 코드 3개 모듈만 AWS 컨테이너의 별도 Python 프로세스 메모리에 로드한다.
운영 파일·서비스·DB 대화·배포 설정은 바꾸지 않는다. `.env`·키 파일은 열거나 전송하지 않는다.
모델·effort·DB·Qdrant는 서버 실행 설정을 사용한다. 실행 시 코드 SHA-256과 공개 모델
설정, 시작 시각, 검색기 사전 초기화 시간을 기록한다.

양쪽 모두 새 Claude 클라이언트·빈 대화 문맥이며 검색기는 같은 프로세스에서 재사용한다.
지연은 서비스 `reply` 진입~반환이다. HTTP 인증·대화 저장·SSE·브라우저 표시와
trace flush/close는 제외한다. 비교 전 검색기 초기화 시간도 양쪽에서 제외한다.
운영 동시 트래픽과 외부 API 변동은 통제하지 못하므로 소규모 비교로 해석한다.

출력은 원시 JSONL, `.summary.json`, `.md` 표다. 사용자 질문 횟수와 LLM 호출 횟수를
구분하고 호출별 시간·턴별 도구·검토 횟수·상태 변화를 함께 본다. 빨리 실패한 응답을
성능 향상으로 계산하지 말고 동일 상태로 끝난 쌍을 별도로 비교한다.
서비스 `OK`와 모델 검토 통과는 사람의 사실 정확성 검수를 대신하지 않는다.

결과는 Git 제외 대상 `outputs/`에 보관한다. 실제 실행 수치는
[CHAT_ROUNDTRIP_RESULTS](CHAT_ROUNDTRIP_RESULTS.md)에 별도로 기록한다.

## 결과 해석

현재 실행기는 동일 코드에서 프롬프트 4개를 교체하므로 v10의 전체 배포 코드와
현재 코드를 비교하는 실험이 아니다. COUNT_ONLY 코드 도입 전후 효과도 이 실험만으로
분리하지 않는다. 같은 턴의 다중 조회는 서버의 병렬 실행과 다르다.

v12 지연 수치는 `data/eval/chat_prompt_v12_latency_20261106.json`에 보존돼 있다.
v13의 호출·지연·사람 답변 검수는 별도 측정해야 한다. 문자 수 감소를 토큰·시간
감소로 환산하지 않는다. 사용자 질문 수·작성 턴·전체 LLM 호출·HTTP 시도·검토 횟수,
동일 비실패 상태 쌍과 상태가 바뀐 쌍을 나누어 보고한다.
