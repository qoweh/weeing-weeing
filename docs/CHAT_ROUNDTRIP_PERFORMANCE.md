# 챗봇 LLM 왕복·재작성 개선 (#214)

모델·effort·검증 횟수 상한을 바꾸지 않고, 필요한 근거를 모은 뒤 첫 답변이 검토를
통과하도록 개선한다. 인용 존재·최신 판·승인 상태·검토 후 출처 확인은 유지한다.

## 변경 동작

- 일반 점검 질문은 매뉴얼부터 조회한다. 질문에 과거 사례 요구가 없으면 이력을
  의무적으로 추가 검색하지 않는다. 독립적인 조회는 같은 LLM 턴에 요청하도록 안내한다.
  공용 Agent 실행기를 병렬화하거나 의존하는 도구 실행 순서를 바꾸지 않는다.
- `search_knowledge` 내부 결과는 `hits`, `availability`, `scope_source` 객체다.
  외부 HTTP 검색 계약과 `ChatKnowledge.search()`의 목록 반환은 그대로다.
- 이력 검색 결과가 비면 같은 도구 실행 안에서 기존 `query_history`로 DB 범위를 확인한다.
  조건·코드가 일치하고 0건 출처의 최신 상태가 확인된 경우에만 `NO_CANDIDATES`와
  인용 가능한 `HISTORY_QUERY` 출처를 함께 반환한다. 검색어를 바꾸거나 같은 건수를
  별도 LLM 턴으로 다시 조회할 필요가 없어진다.
- 승인 보고서는 있는데 벡터 검색이 비면 `NO_MATCHES`, 매뉴얼 검색이 비거나 범위 조회를
  제공하지 않는 검색기이면 `NO_RESULTS`다. 둘 다 자료 자체가 없다는 뜻은 아니다.
  색인 누락·필터·검색어 문제일 수 있어 필요한 재검색은 허용한다.
- 0건은 현재 조회 조건에 맞는 최신 승인 보고서 수다. 전체 고장 횟수나 모든 원본 기록의
  부재로 일반화하지 않는다. 같은 요청 안에서도 제출 전·검토 후 출처를 다시 확인한다.
- 근거 검토 응답에 문제 부분 번호와 정해진 이유 코드를 추가한다. 자유 생성 지시 대신
  서버의 고정된 수정 안내를 작성 모델에 전달한다. 수정 뒤에도 같은 근거 검토를 실행한다.
- 첫 답변의 근거 수준·자료별 인용·조회 범위 표현을 명시하고, 지시 대상만 없는 질문은
  어떤 문제/알림인지 최소 확인 질문을 하도록 작성·검토 지침을 맞춘다.
- 기존 최종 응답 계약을 근거 검토 전에 검증한다. 상태·의도·본문·인용 조합 오류로
  유료 검토와 검토 횟수 예산을 낭비하지 않는다. 형식이 유효한 답변은 이후 같은 근거 검토를 거친다.

## 계측

`service.last_run.calls`는 호출별 목적·모델·시간·토큰·통신 시도 수다.
`service.last_run.reviews`는 검토 모드·판정·문제 부분 번호·이유 코드다.
동일 정보는 `chat` trace의 `reviews` 메타데이터에도 남긴다.
이 메타데이터에는 질문·답변·수정 문장·비밀값이 없다. 기존 Langfuse 본문 수집 정책은 별도다.

이유 코드는 `UNSUPPORTED_CLAIM`, `SCOPE_OVERSTATEMENT`, `CONDITION_CONFLICT`,
`INCOMPLETE_ANSWER`, `UNNECESSARY_CONDITION`, `UNCLEAR_QUESTION`이다.
지원하지 않는 코드나 문제 부분 목록과 불일치하는 번호는 검토 형식 오류로 처리한다.
이전 가짜 검토기의 `issues` 생략은 호환하지만 실제 구조화 요청에는 이 필드도 포함된다.

## 재현 가능한 비교

```bash
# 기본은 계획만 출력하며 SSH/실제 모델을 호출하지 않는다.
uv run --no-env-file --no-sync python scripts/benchmark_chat_roundtrips.py

# 실제 Claude·Voyage 비용 발생. 기존 SSH 별칭/서버 실행 설정 사용.
uv run --no-env-file --no-sync python scripts/benchmark_chat_roundtrips.py \
  --execute --repeats 2 \
  --output outputs/chat_roundtrips/comparison.jsonl
```

고정 10문항을 두 버전으로 각 2회 실행하므로 서비스 요청은 40회다.
`--repeats`는 1~5이며 기본 2다. 같은 출력 파일은 덮어쓰지 않는다.
각 질문의 기존/후보 실행 순서를 교대로 바꿔 한쪽이 항상 먼저 실행되는 편향을 줄인다.

후보 코드 3개 모듈만 AWS 컨테이너의 별도 Python 프로세스 메모리에 로드한다.
운영 파일·서비스·DB 대화·배포 설정은 바꾸지 않는다. `.env`·키 파일은 열거나 전송하지 않는다.
모델·effort·DB·Qdrant는 서버 실행 설정을 사용한다. 실행 시 코드 SHA-256과 공개 모델
설정, 시작 시각, 검색기 사전 초기화 시간을 기록한다.

양쪽 모두 새 Claude 클라이언트·빈 대화 문맥이며 검색기는 같은 프로세스에서 재사용한다.
지연은 서비스 `reply` 진입~반환이다. HTTP 인증·대화 저장·SSE·브라우저 표시와
trace flush/close는 제외한다. 비교 전 검색기 초기화 시간도 양쪽에서 제외한다.
운영 동시 트래픽과 외부 API 변동은 통제하지 못하므로 소규모 비교로 해석한다.

출력은 원시 JSONL, `.summary.json`, `.md` 표다. 사용자 질문 횟수와 LLM 호출 횟수를
구분하고 호출별 시간·턴별 도구·검토 횟수·상태 변화를 함께 본다. 빨리 실패한 응답을
성능 향상으로 계산하지 말고 동일 상태로 끝난 쌍을 별도로 비교한다.
서비스 `OK`와 모델 검토 통과는 사람의 사실 정확성 검수를 대신하지 않는다.

결과는 Git 제외 대상 `outputs/`에 보관한다. 실제 실행 수치는
[CHAT_ROUNDTRIP_RESULTS](CHAT_ROUNDTRIP_RESULTS.md)에 별도로 기록한다.
