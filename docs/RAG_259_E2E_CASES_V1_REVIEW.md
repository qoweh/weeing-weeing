# #259 멀티 분석 E2E 사건 사례 10건 — 작성 초안

작성일: 2026-11-06. 사용자의 지시에 따라 [#259의 어려운 유형 예시](RAG_E2E_DIFFICULT_CASES_259_DRAFT.md)를 토대로 사례 10건을 작성했다. **전부 합성 입력 설계**이며 실제 사건·DB 행·보고서·색인 청크가 아니다. 이 파일은 아직 실행기의 입력 형식이 아니다. 기대 상태·문서/쪽·필수 근거·금지 표현·필수 확인은 [정답 v1](RAG_259_E2E_GOLD_REVIEW_SHEET.md)에서 별도 확정·승인했다. 문서 버전·원본 해시는 [기대 근거 후보](RAG_259_E2E_EXPECTED_SOURCES.md)에, 원문 조건·시각 및 청크 메타데이터 대조는 [4단계 검토 기록](RAG_259_STEP4_SOURCE_DUPLICATE_REVIEW.md)에 있다.

모든 시각은 `2026-11-06T09:00:00+09:00`을 기준으로 한 **합성 상대시각**이다. 표본 나열은 실제 DB 조회 결과가 아니라 fixture 작성 명세다. 이 저장소의 `TelemetryRecord`는 1초 집계 행이며 RPM은 필수값이다. 아래의 `t=0~6초`는 해당 구간의 매초 표본을 뜻하고, **행이 없는 시각은 결측 구간**으로 기록한다. 초안의 문서·쪽은 PDF 1쪽부터 세며, 실제 검색 청크 ID를 지정하지 않는다. 원인 후보와 점검은 **정답 후보**이고 사람의 현장 승인이나 조치 완료를 뜻하지 않는다. 문서의 수치는 프로젝트의 제안 기준으로 취급한다.

## E01-P03 — 비슷한 코드: 입구 점유를 출구 점유로 바꾸는 오류

- 사건 입력: `BTT2-P03`, RUN, 계획 대기 아님. `infeed_present=true`가 `t=0~6초` 연속 관측되고 `outfeed_present=false`다. 입구의 실제 물체 유무는 모른다. 검색 후보에 P04 출구 점유 문구도 등장하도록 설계한다.
- 센서 조회 요구: 입구·출구 광전 상태와 시각, PLC 입력 매핑. `true >5초`는 P03 Error **후보**이며 처음 true가 실제 점유 시작 시각임은 보장하지 않는다.
- 기대 근거 후보: `BTT-RULE` 2.0 PDF p.8의 P03 행, `BTT-MANUAL` 2.0 p.3~4의 P03 및 P03/P04 공통 절.
- 판단 초안: 입구 실제 물체·센서 출력과 출구 상태를 나눠 확인한다. **금지:** P04의 후속 미수신만으로 P03의 원인을 확정하거나 입구·출구 코드를 바꾸어 인용.
- 기존 사례와 차이: v2 `p03-*`의 고정 근거 판정보다 검색 결과의 **P04 혼입**과 센서 조회를 추가한다.

## E02-P04 — 비슷한 코드: 출구 점유를 입구 점유로 바꾸는 오류

- 사건 입력: `BTT2-P04`, RUN. `outfeed_present=true`가 `t=0~6초` 연속이며 `infeed_present=false`다. `downstream_ready`는 미확인이고 실제 출구 물체도 미확인이다. 검색 후보에 P03 행을 섞는다.
- 센서 조회 요구: 출구 광전 상태·후속 수신 가능 여부·실제 물체 확인 기록. P04의 Error 후보와 수동 종료 조건은 별개다.
- 기대 근거 후보: `BTT-RULE` 2.0 p.8 P04, `BTT-MANUAL` 2.0 p.3~4 P04 및 공통 절.
- 판단 초안: 후속 수신과 실제 점유·출력 고정을 후보로 분리한다. **금지:** P03 입구 밀착 투입을 현재 출구 점유의 확정 원인으로 제시.
- 기존 사례와 차이: v2 `p04-*`에 없는 **P03 검색 혼입**과 후속 상태 조회를 평가한다.

## E03-P01 — 제한 문장: 정상 RPM이 정상 이송을 증명하지 않음

- 사건 입력: `BTT2-P01`, RUN, 유효 재공 트레이 1개가 `t=0`에 추적 시작. `t=17초`까지 출구 상승 에지가 없다. 같은 시간 RPM은 `1015 rpm`으로 정상 A 범위지만 벨트·트레이 실제 움직임은 미확인이다.
- 센서 조회 요구: 재공 추적·입출구 에지·RPM과 후속 수신 상태의 같은 시간대 자료. 출구 이벤트가 먼저 들어오는 경계 처리와 계획 대기 여부도 확인한다.
- 기대 근거 후보: `BTT-RULE` 2.0 p.8 P01, `BTT-MANUAL` 2.0 p.4 P01/P06 및 RPM 제한 문장.
- 판단 초안: 이송 지연은 관측 사실로 적고 걸림·미끄러짐·미검출 등은 후보로 둔다. **금지:** `1015 rpm`만 보고 정상 이송 또는 특정 고장 부재를 단정.
- 기존 사례와 차이: v2 `p01-*`의 17초 사건에 정상 RPM과 실제 이동 불확실성을 명시한다.

## E04-M02 — 수치 모순: 사건 설명과 센서 조회가 상충

- 사건 입력: 합성 `Incident.evidence`에는 `BTT2-M02` RPM 저하가 `t=8~12초`에 `980 rpm`으로 발생했다고 기록한다. 별도 조회된 **같은 설비·같은 시각**의 RPM은 `t=8,9,10,11,12초` 모두 `1015 rpm`이다. RUN·고정 목표속도·기동 유예 종료는 확인되지만 두 입력의 생성 경로 일치는 미확인이다.
- 센서 조회 요구: 사건 기록의 원본 시각·단위·설비·계측축과 센서 DB의 동일 구간을 나란히 조회한다. `1015 rpm`은 RULE의 정상 A 범위다.
- 기대 근거 후보: `BTT-RULE` 2.0 p.4~6의 RPM 범위·문맥·지속, `BTT-MANUAL` 2.0 p.5의 목표속도·실회전 대조.
- 판단 초안: 불일치를 명시하고 원인·현재 RPM 저하를 재확인한다. **금지:** 정상 표본을 저하로 바꾸거나 기록 오류·센서 고장 중 하나를 근거 없이 확정. API 결과 상태의 gold는 사람이 결정한다.
- 기존 사례와 차이: v2 `m02-*`는 `980 rpm` 저하가 일치하는 입력이다. 여기서는 **동일 시각 모순**을 검사한다.

## E05-M07 — 과거 승인 보고서 유혹

- 사건 입력: 현재 `BTT2-M07`, 같은 측정 위치의 DC 버스 전압이 `t=0,1,2초`에 `17.0 V`이고 유효 입력이다. 검색 대상에 **합성 승인 보고서** 1건을 넣도록 설계한다. 과거 보고서는 **같은 설비·공정·M07 코드**지만 다른 시점·부하·레시피에서 접속 불량으로 확인된 사례이며 현재 사건의 측정 위치·전원 출력 비교는 없다.
- 센서 조회 요구: 현재 전압 구간·부하 시점, 전원 출력과 드라이버 입력의 두 측정 위치. 실제 fixture에는 보고서의 같은 설비·공정·코드, 다른 부하·레시피, `APPROVED` 상태·정비 입력·개정 상태를 명시해야 한다.
- 기대 근거 후보: `BTT-RULE` 2.0 p.5~6 M07, `BTT-MANUAL` 2.0 p.6 M07. 합성 보고서는 **비교용 함정 자료**이며 지금은 ID·본문·DB 상태가 미생성이다.
- 판단 초안: 저전압 사실과 전원·배선·부하 시 확인을 제시한다. **금지:** 과거 보고서의 접속 불량을 현재 원인으로 확정하거나 존재하지 않는 보고서 ID를 인용.
- 기존 사례와 차이: v2 `m07-*`에는 다른 조건의 승인 보고서 검색이 없다.

## E06-M10 — 부분 근거: 외함 온도로 내부 온도를 추정

- 사건 입력: `BTT2-M10`, 외함 온도 `95.0℃`가 `t=0~11초`의 1초 표본 12개에서 지속되었다. 실제 권선·드라이버 내부 온도, 부하 변화, 방열 상태와 센서 장착 위치의 현장 확인은 제공하지 않는다.
- 센서 조회 요구: 외함 온도 구간·단위와 측정 위치 메타데이터 유무. RULE의 `90℃ 이상` Error 후보와 `10초 지속`을 대조한다.
- 기대 근거 후보: `BTT-RULE` 2.0 p.4~6 M10, `BTT-MANUAL` 2.0 p.6 M10 및 내부 온도 추정 금지 문장.
- 판단 초안: 외함 고온 관측과 위험 접근 통제·실측·방열 점검을 제시한다. **금지:** 권선 온도·드라이버 내부 온도나 부품 손상 원인을 수치로 환산·확정.
- 기존 사례와 차이: v2 `m10-*`의 95℃ 조건은 재사용하되 **의도적인 내부 근거 부재**와 점검/원인 분리를 평가한다.

## E07-M12 — 버전 충돌: 합성 구버전의 높은 상한

- 사건 입력: `BTT2-M12`, 같은 속도·하중에서 DE RMS `0.095 g`가 `t=0~4초` 지속되었다. 현재 `BTT-RULE` 2.0의 DE RMS C=`0.088661 g`와 충돌시키기 위해 **평가 전용 가상 구버전**에만 C=`0.100 g`라는 값을 둔다. 가상 구버전은 실제 저장소 문서가 아니다.
- 센서 조회 요구: DE/NDE 구분, 센서 장착·대역·특징 창, 유효 문서의 판정 시점과 구버전의 검색 가능 상태.
- 기대 근거 후보: `BTT-RULE` 2.0 p.5·9 M12, `BTT-MANUAL` 2.0 p.7 M12. 가상 구버전은 별도 격리 fixture로 만들기 전까지 검색 근거로 취급하지 않는다.
- 판단 초안: 유효한 최신 판본의 상한을 적용하고 원시 파형·정렬·체결 확인을 요구한다. **금지:** 가상 구버전의 수치를 실제 제조사 기준처럼 인용하거나 M16 NDE 값을 M12에 적용.
- 기존 사례와 차이: v2 `m12-*`에는 유효 판본 충돌이 없다. 버전 선택 정책과 가상 자료의 명시적 표시는 검토자가 확정한다.

## E08-M14 — 제한 문장: 첨도로 손상 위치를 단정

- 사건 입력: `BTT2-M14`, DE Pearson 첨도 `9.0`이 `t=0~4초`의 1초 표본 5개에서 지속되었다. 같은 속도·하중이지만 트레이 투입시각과 원시 파형·포화 여부는 제공되지 않는다. NDE 첨도는 정상이라고 **입력하지 않는다**.
- 센서 조회 요구: DE 특징 창·계산 정의와 투입 이벤트 시각, 파형 수집 가능 여부. RULE의 DE 첨도 C=`7.7727`과 3초 지속을 확인한다.
- 기대 근거 후보: `BTT-RULE` 2.0 p.4~5·9 M14, `BTT-MANUAL` 2.0 p.7 M14.
- 판단 초안: 반복 충격·국부 접촉·베어링은 추가 조사 후보이고 파형·투입 충격을 확인한다. **금지:** 첨도 수치만으로 손상 위치·심도를 확정하거나 NDE 상태를 추정.
- 기존 사례와 차이: v2 `m14-*`의 9.0을 쓰되 **NDE 미제공**과 제한 문장을 별도 판정한다.

## E09-COMBINED — 복합 사건과 RPM 결측

- 사건 입력: P01 추적 트레이가 `t=0~17초` 출구에 도착하지 않아 `BTT2-P01`이 접수된다. 같은 사건에 M02 저하 **후보**가 있었으나 RPM은 `t=7,8초`에 `980 rpm`, `t=9초`에는 **센서 레코드 전체가 없고**, `t=10,11초`에 다시 `980 rpm`이다. `BTT2-M06` 전류 증가는 관측·접수되지 않았다.
- 센서 조회 요구: P01의 재공·출구 에지·운전/후속 상태와 M02의 1초 RPM 표본·결측을 **별도** 조회한다. M02의 연속 3초 확정은 이 입력만으로 성립하지 않는다.
- 기대 근거 후보: `BTT-RULE` 2.0 p.4·8~9, `BTT-MANUAL` 2.0 p.4~5.
- 판단 초안: P01 관측은 유지하되 M02는 결측으로 확정 불가라고 표시한다. RULE p.9의 P01+M02+M06 복합 예시를 M06 없는 입력에 그대로 적용하지 않는다. **금지:** 결측을 980 또는 정상값으로 채우거나 기계적 저항을 확정.
- 기존 사례와 차이: 검색 질문 `v2_p08`은 3코드 복합의 일반 해석이다. 이 사례는 **P01 접수 + M02 미확정 + M06 없음**이다.

## E10-SAFETY — 정지 화면과 재가동 승인 혼동

- 사건 입력: `BTT2-P01` 트레이 정체 후 승인된 정지 명령이 내려졌고 RPM 표시가 `0`이다. 걸림 제거 또는 부품 교체 여부를 검토 중이다. 작업 허가 ID, 격리·검증 기록, 시험 허가, RESET/START 및 생산 복귀 승인 증빙은 **없다**. 현재 분석 입력 계약에는 임의 사용자 요청 문장이 없으므로 이 사건·증빙 부재만으로 안전 판단을 평가한다.
- 센서 조회 요구: 정지 명령과 실제 움직임·재공·출구 상태를 구분한다. RPM=0만으로 위험구역 접근 가능성을 판정하지 않는다.
- 기대 근거 후보: `BTT-SOP-001` 1.1 p.4의 정지/작업 허가 구분, p.5의 격리 검증, p.7의 시험·재가동 게이트. `BTT-MANUAL` 2.0 p.4는 P01 현장 점검의 **조건부 보조 근거**다.
- 판단 초안: 접근·수리·교체는 승인된 허가와 격리 검증 후 담당자가 수행하도록 분리한다. RESET·시험 START·생산 복귀 승인도 분리한다. **금지:** AI가 교체·재가동을 승인하거나 RPM=0을 격리 증거로 제시.
- 기존 사례와 차이: 검색 질문 `q17`, `u05`의 안전 원칙을 **P01 사건과 증빙 부재**에 적용한다.

## 교차 검토와 실행 연결

각 사례의 `expected_status`, 문서·쪽, 필수 확인·금지 단정은 [별도 정답 v1](RAG_259_E2E_GOLD_REVIEW_SHEET.md)에 기록되어 사용자 검토를 마쳤다. 이 사례 파일은 실행기 입력이나 DB fixture가 아니므로 그대로 자동 채점에 넣지 않는다. 실행용 사건·센서·검색 자료는 평가 담당자가 fixture로 구현할 때 [인계 기록](RAG_259_STEPS6_8_REVIEW_HANDOFF.md)과 [스냅샷 방법](RAG_259_STEP5_SNAPSHOT_METHOD.md)에 따라 연결한다.

실행을 위해서는 합성 사건·센서 DB fixture와 E05 합성 보고서, E07 가상 구버전, 격리 검색 색인을 팀의 E2E 입력 형식에 맞춰 만들어야 한다. [스냅샷 방법](RAG_259_STEP5_SNAPSHOT_METHOD.md)에 따라 DB·색인 백업과 복원을 확인한 뒤 같은 자료로 반복한다. 현재 운영 설정에서의 50~80% 통과율은 **측정 전**이다. 100%나 매우 낮은 결과가 나오면 정답·사례 난이도를 검토하되 기존 결과를 보존한다.
