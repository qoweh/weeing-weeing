# 개인 대화 저장·중복 요청 정책 (#90)

## 필요한 구성만 유지

이번 구현은 대화 저장·본인 접근·중복 실행 방지로 범위를 제한한다.

| 구성 | 판단·이유 |
|---|---|
| ChatSubmission | 유지: 자유 질문과 FAQ 선택을 검증하고 재전송 ID를 전달 |
| ChatRequestView | 유지: 처리 중·완료·안전한 재시도·결과 불명을 구분 |
| ChatSavedMessage | 유지: 질문/답변의 원문·순번·시각·출처를 다시 표시 |
| ChatConversationPage | 유지: 긴 대화 기록을 제한된 크기로 조회 |
| ChatSavedConversation | 삭제: 기존 ChatConversation에 FAQ/CHAT 모드를 합침 |
| ChatUsageCall / ChatSavedUsage | 삭제: 별도 사용량 영구 저장은 이번 요구 범위에 불필요 |
| ChatSourceState | 삭제: 과거 기록 열람에 현재 검색기 상태를 요구하지 않음 |
| ChatFeedback | 삭제: 응답 평가 기능은 이번 요구 범위에 불필요 |

공개 저장소는 `db.interface.get_chats/open_chats`, 실행 조립은
`api.chat_storage.StoredChatService`다. 조회·수정·삭제는 DB 저장소를 바로 사용하며
실행 조립 계층에 똑같은 조회 함수를 다시 두지 않는다.
기존 에이전트의 사용량 수집과 새 답변의 검색·인용 검증은 유지한다.

HTTP 라우트·인증은 #91에 연결했다([CHAT_API](CHAT_API.md)). 화면은 #92에서 연결한다.
HTTP는 로그인 세션의 사번을 actor_id로 전달해야 한다. 사용자가 본문에 지정한
사용자 ID·소유자·이전 문맥·실행 토큰은 받지 않는다.
기존 `make chat-private`의 익명 대화는 영구 저장하지 않는다.

## 본인만 접근·기록 보존

모든 작업에서 활성 계정과 대화 소유자를 DB에서 확인하며 관리자 예외는 없다.
목록은 본인 대화만 반환하고, 타인 대화와 없는 대화는 동일 ChatNotFoundError다.
문서·보고서 공통 열람 정책은 유지하고 개인 대화는 공통 검색 색인에 넣지 않는다.
애플리케이션 사용자 간 접근을 차단하며 DB 운영자의 직접 SQL 접근을 막는 암호화/RLS는 별도다.

사용하는 테이블은 chat_conversation(소유자·제목·조건·모드), chat_request(요청·상태·응답),
chat_message(순서가 있는 질문/답변)다. FAQ는 선택 당시 대표 질문·답변·출처 ID를 저장한다.
과거 기록은 당시 내용 그대로 반환하며 최신 자료라는 보장은 하지 않는다.
새 답변에는 기존 ChatService의 검색·출처 검증을 적용한다.
API 키·시스템/도구 프롬프트·공급자 원문·예외 메시지는 저장하지 않는다.
사용자가 직접 질문에 입력한 내용은 저장되므로 키를 질문에 입력하면 안 된다.

소유자가 삭제할 때까지 보관하며 삭제 시 해당 요청·메시지도 함께 지운다.
기존 사용자·보고서는 유지한다. 백업 삭제는 DB 운영 정책 대상이다.

## 중복·실패 처리

새 질문은 새 UUID를 사용하고 같은 질문의 네트워크 재전송에는 원래 ID를 유지한다.
중복 판정은 대화별 request_id와 정규화 본문이다. 다른 본문을 같은 ID로 보내면 충돌한다.
조건 생략은 첫 예약의 대화 조건으로 고정하므로 이후 선택 조건을 바꿔도 과거 요청을 다시 볼 수 있다.

| 상태 | 동일 요청을 재전송하면 |
|---|---|
| RESERVED | 실행 전 상태 반환, 추가 실행 없음 |
| RUNNING | 처리 중 상태 반환, 추가 실행 없음 |
| COMPLETED | 저장 응답 반환. 응답 자체가 FAILED여도 재생성하지 않음 |
| FAILED | 실패 상태 반환. retry_allowed=true이고 retry=True를 명시한 경우만 재예약 |
| UNKNOWN | 결과 불명 상태 반환, 같은 ID 재실행 불가 |

실행 전/후를 구분해야 과금 여부가 불확실한 요청을 다시 실행하지 않을 수 있다.
실행 전 일시적 실패만 안전한 재시도를 허용하고 실행 후 예외는 UNKNOWN이다.
FAQ ID 오류는 FAILED에 구체 코드를 저장하지만 같은 ID 재실행은 허용하지 않는다.
ChatResponse.failure.retryable은 장애 회복 가능성이지 같은 ID의 재실행 허가가 아니다.

한 대화에는 한 요청만 처리하며 그동안 모드·선택 조건을 변경하지 않는다.
새 대화는 FAQ 모드이며 채팅 시작은 소유자의 mode="CHAT" 갱신으로 연결한다.
CHAT에서도 FAQ 선택이 가능하다.
PostgreSQL 행 잠금/SQLite BEGIN IMMEDIATE로 예약하고 실행 토큰은 외부에 노출하지 않는다.
외부 호출 직전에 RUNNING을 커밋하고 호출 중 DB 잠금을 유지하지 않는다.
요청별 전용 ChatService를 사용해 서로 다른 대화에 불필요한 전역 실행 잠금을 걸지 않는다.
응답·메시지·상태는 한 트랜잭션으로 저장한다. 같은 실행 토큰·동일 응답의 완료 저장은 재호출할 수 있다.

예약은 기본 900초(서버 내부 1~3600초), LLM 예산은 기본 120초·최대 600초다.
조회·예약·갱신·완료 시 만료를 확인한다. 실행 전 만료는 재예약 가능 실패,
실행 후 만료는 UNKNOWN이며 늦게 돌아온 이전 토큰으로 결과를 덮어쓰지 못한다.
만료가 이미 진행 중인 네트워크 호출을 취소하지는 않으며 자동 재실행 작업은 없다.
외부 LLM과 DB는 한 트랜잭션이 아니므로 생성 후 저장 실패 시 응답이 남지 않을 수 있다.
이때 재전송으로 다시 생성하지 않는다. UNKNOWN 이후 새 ID 전송은 새 실행으로 비용이 발생할 수 있다.
공급자 내부의 제한된 통신 재시도는 요청 재실행 정책과 별개다.

최근 문맥은 본인 대화의 완료된 10쌍 중 실패 응답을 제외하고 서버가 구성한다.
각 메시지 4000자·합계 16000자로 제한하며 이것을 현재 검색 근거로 취급하지 않는다.

## 기존 DB 호환·검증

기존 데이터 삭제는 하지 않는다. 이전 JSON에 남은 FAQ 버전은 조회할 때만 제외하며
중복 요청 비교에서도 폐지한 버전을 무시한다. 과거 질문·답변을 재생성하지 않는다. 0007 마이그레이션과 기존 피드백 테이블·사용량 컬럼은
호환을 위해 유지하며 기능 코드·공개 계약에서는 사용하지 않는다. DB 모델의
LegacyChatFeedbackRow와 usage 선언은 이 스키마를 보존하는 용도다.
이미 0007을 적용했다면 코드 정리 때문에 DB를 다시 만들 필요가 없다.
0007 미적용 개발 DB는 사용자가 로컬에서 `make db-migrate`로 반영한다.
테스트에서는 임시 DB만 사용한다.

```sh
UV_NO_ENV_FILE=1 uv run --no-sync --no-env-file pytest -q tests/contracts/test_chat_storage_contract.py tests/db/test_chat_storage.py tests/api/test_stored_chat_service.py
UV_NO_ENV_FILE=1 make check
```

PostgreSQL 검증은 삭제 가능한 별도 TEST_DATABASE_URL에서 tests/db를 실행한다.
기존 데이터가 있는 DB를 테스트 URL로 지정하면 안 된다(테스트가 테이블을 비운다).
