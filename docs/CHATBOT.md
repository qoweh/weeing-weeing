# 챗봇 계약과 후속 연결

상위 [#85](https://github.com/qoweh/weeing-weeing/issues/85), 공통 계약은
[#86](https://github.com/qoweh/weeing-weeing/issues/86), 파일 기반 FAQ 선택 조회는
[#87](https://github.com/qoweh/weeing-weeing/issues/87)의 범위다.
FAQ 조회·자유 대화 도구 루프·실제 DB/RAG 검색 연결과 CLI를 구현했다. 개인 대화 저장·중복 요청 처리·실행 조립은 #90에 추가했다. 챗봇 HTTP API는 #91의 `api/chat.py`에 연결했고 화면은 후속 작업이다.
정확한 계약은 [CONTRACTS](CONTRACTS.md)의 챗봇 절을 따른다.

## 첫 단계 사용 예

```python
from uuid import uuid4

from weeing_weeing.contracts import ChatQuestion, ChatSearchConditions

question = ChatQuestion(
    request_id=uuid4(),
    question="입구 센서 장기 점유의 매뉴얼 기준과 과거 사례를 알려줘",
    conditions=ChatSearchConditions(asset_id="BLDC-001", limit=5),
)
```

자유 질문은 별도 사전 분류 없이 Claude의 도구 호출 흐름으로 전달한다.
클라이언트의 사용자 ID·과거 대화·권한 지정은 받지 않는다.
문서 원문은 로그인 사용자에게 공통 열람한다. 보고서의 초안·반려·과거 판도 포함한다.
API는 로그인·본인 대화 소유권을 검사하고 조건·출처 상태 검증 검색기를 주입한다.
대화 재조회 때는 본인 소유권과 인용 문서의 삭제·개정 상태를 확인한다.
보고서 작성·수정·제출·결재 권한은 문서 열람과 별개이며 기존 규칙을 유지한다.

## FAQ 주제·질문 선택 (구현)

챗봇을 열면 **주제→세부 질문→검토 답변**을 탐색한다. FAQ ID로 선택하므로
의도 분류·문장 매칭·임베딩·LLM을 호출하지 않는다. **채팅 시작** 버튼은 주제 목록,
질문 목록, FAQ 답변을 보는 동안 항상 표시한다(#92 화면 후속 구현).
버튼으로 전환한 후에만 자유 입력창을 열고, 실제 질문 전송 때 자유 대화 경로를 호출한다.
버튼 클릭 자체로 검색·LLM을 실행하지 않는다.

저장소 루트에서 `PYTHONPATH=src uv run --no-sync python`을 실행한 뒤 다음 예제로
조회할 수 있다. 프로젝트 자체를 설치하지 않으므로 직접 실행 시 src 경로가 필요하다.

```python
from uuid import uuid4

from weeing_weeing.agent.interface import load_faq_catalog
from weeing_weeing.contracts import FaqSelection

catalog = load_faq_catalog()
topics = catalog.list_topics()
questions = catalog.list_questions(topics[0].topic_id)
question = questions[0]
snapshot = catalog.get_answer(question.faq_id)
response = catalog.answer(
    FaqSelection(
        request_id=uuid4(),
        faq_id=question.faq_id,
    )
)
# snapshot.question / snapshot.answer: 서버 데이터로 저장할 질문·답변
# response.parts[0].text: 그대로 표시할 검토 답변
```

API 키·DB·모델 다운로드 없이 동작한다. API 구현 시 일반 이용 안내 FAQ도 기존 인증
정책에 맞춰 연결하며 인증·대화 소유권 검사는 서버에서 수행한다. FAQ는 권한을
변경하거나 실제 계정·보고서·설비 상태를 조회하지 않는다.

### 데이터·활성 규칙

- 파일은 `data/faq/service_v1.toml`, `schema_version=1`이다. `topics`는 ID·제목·
  표시 순서·active, `faqs`는 ID·주제·대표 질문·순서·active·유사 표현·답변을 가진다.
  유사 표현은 참고 자료이며 현재 자동 매칭하지 않는다.
- ID는 안정적으로 유지하며 재사용하지 않는다. 수동 FAQ 버전·검토일·참고 문서 필드는 없다.
  선택 시 같은 ID의 현재 답변을 반환하고 이미 저장한 대화는 당시 내용을 보존한다.
- `active` 기본값은 false다. 활성 질문에는 비어 있지 않은 답변이 필요하다.
  ID 중복·없는 주제 참조·알 수 없는 필드는 파일 로드 실패다.
- 활성 주제와 활성 질문의 교집합만 제공한다. 비활성 질문은 직접 ID 조회도 불가하며
  공개 질문이 없는 주제는 숨긴다. 주제·질문은 order 다음 ID 순으로 정렬한다.
- 현재 목록은 접근·권한, 보고서 관련, 문의 담당 안내의 3개 주제·7개 질문이다.
  승인 순서 질문은 보고서 주제의 `FAQ-REPORT-003`이며 문의는 작성·제출의
  `FAQ-CONTACT-001`, 검토·최종 결재의 `FAQ-CONTACT-002`다. 문의 안내는 현장 점검자·
  보전 팀장·관제 담당자라는 업무 직책 기준이며 개인·전화번호를 추정하지 않는다.
- 사용자 합의에 따라 현장 책임자는 FAQ 안내에서 제외한다. 참고 문서와 기존
  `Role.SITE_MANAGER`에는 아직 남아 있으므로 저장소 전체 역할 제거와 기존 계정·DB
  정리는 별도 변경이 필요하다. FAQ 작업이 기존 권한 모델을 변경하지는 않는다.
- 파일은 로드 시 한 번 읽는 스냅샷이다. 편집 후 `load_faq_catalog()`로 새 인스턴스를
  만들고 API 프로세스를 재시작해 교체한다(#91). 운영 파일 변경은 검토·버전 관리 후 배포한다.

### 오류 정책

| 공개 오류 | 의미 | HTTP 처리 |
|---|---|---|
| `FaqNotFoundError` | 없는/비활성 FAQ, 숨긴/빈 주제. 동일한 안전한 안내 | 404, 목록 새로고침·채팅 시작 안내 |
| `FaqCatalogError` | 파일 없음·구문/데이터 오류 | 503, 운영자 확인 |

카탈로그가 비어 있는 정상 상태는 빈 주제 목록이다. 파일 장애를 빈 목록으로 숨기지
않고, 어떤 오류도 LLM 자동 호출로 처리하지 않는다. UI는 FAQ 조회 실패에도 채팅 시작
버튼을 숨기지 않는다. 대화 저장·중복 예약·최근 문맥 복원은 #90에 구현했고 HTTP는 #91에 연결했고 화면은 #92에서 한다.

검사: `uv run --no-sync pytest tests/contracts/test_faq_contracts.py tests/agent/test_faq.py`.
목록/선택·활성 상태·중복 ID·파일 오류·복사 격리·외부 서비스 미호출을 검증한다.
별도 사전 분류기·조건 추출 호출은 #87에 포함하지 않는다. 자유 질문은 #89의
Claude 도구 호출 흐름 안에서 처리한다. 실제 검색·출처 상태는 #88 구현을 사용하며 인증된 HTTP API는 #91의 `api/chat.py`에 연결했다.

## 자유 질문과 Claude 도구 호출

`agent.interface.get_chat_service(knowledge, ...)`가 기존 Claude `create()`와
공용 실행기를 재사용한다.
챗봇만 다른 effort(`CHAT_LLM_EFFORT`)나 근거 검토 전용 모델·effort(`CHAT_REVIEW_MODEL`·`CHAT_REVIEW_EFFORT`)를
쓸 수 있다. 비우면 공용 `LLM_MODEL`·`LLM_EFFORT`와 같다(#216·#217, 비교 방법은 [LLM_EVALUATION](LLM_EVALUATION.md)의 지연 기준선). 사용자의 질문을 먼저 다른 분류 모델에 보내지 않는다.
Claude가 `search_knowledge`의 문서 종류·검색어·설비·모델·오류 코드·기간을 선택하고,
`submit_answer`로 검증할 답변을 제출한다. 모호하면 확인 질문을 제출할 수 있다.
자유 질문에 FAQ 내용이 포함되면 `browse_faq`·`get_faq_answer` 도구를 사용할 수 있다.
목록 클릭은 기존 FAQ 직접 반환 경로를 사용하므로 이 루프나 LLM을 거치지 않는다.

검색 입력은 `ChatSearchQuery`, 검색 출력은 `ChatSearchHit` 계약을 사용한다.
`ChatKnowledge`는 사용자별 문서 ACL이 없는 공통 검색 의존성이며, 원시 전역
`Retriever`를 직접 넘기지 않는다. `api.chat_knowledge.DatabaseChatKnowledge`가 공개 DB·RAG
인터페이스로 다음을 구현한다. API는 `build_chat_service()`를 사용한다.

- `validate_query`: 실제 설비·모델·기간과 지원 필터를 검증한다. 미지원 조건을 무시해
  검색 범위를 넓히지 않는다. 잘못되거나 모호하면 `InvalidChatQueryError`다.
  사용자 직책·작성자에 따른 열람 제한은 하지 않는다. 오류에는 비밀값을 담지 않는다.
- `search`: 최신 승인 판·필터 등 검색 대상 정책을 적용하고, 관련 근거의
  최소 본문과 페이지/절·가상 여부 등 서버 메타데이터로 만든 출처를 반환한다.
  유사 검색 개수를 전체 건수라고 답하지 않는다.
- `query_history`: DB의 전체 최신 승인 판에서 설비·코드·실제 조치일을 적용한다.
  전체 보고서 수·가상 보고서 수와 제한된 목록, 0건을 포함한 DB 조회 출처를 반환한다.
  목록의 truncated를 확인하며 보고서 수를 설비의 전체 고장 발생 횟수로 표현하지 않는다.
- `is_searchable`: 검색 후와 답변 출처 반환 전에 삭제·개정·승인 상태를 확인한다.
  직책별 권한 검사가 아니다. 상태 변경·확인 장애는 SEARCH_UNAVAILABLE로 구분한다.
  같은 단계의 여러 출처는 `are_searchable`(선택 구현)로 한 번에 재확인하며, 문서·보고서 목록을 그 호출에서 한 번씩만 읽는다(#220). 없으면 출처마다 `is_searchable`을 부른다.
  원문은 초안·반려까지 읽을 수 있지만 챗봇의 정비 근거는 최신 승인 판만 사용한다.

선택된 설비·모델·기간은 보존하며 모델이 다른 값으로 바꾸면 도구 오류로 반환한다.
검색 결과 개수는 화면 상한을 넘지 않으며 한 답변에서 서로 다른 검색 조건을 섞지 않는다.
한국 시간 기준 날짜를 모델에게 전달하되 상대 기간 해석의 정확성은 서버 검색기에서
확인해야 한다. 이전 대화는 API가 소유권·개인정보·길이를 검증한 `ChatContext`만 받는다.

질문의 핵심 키워드와 의미 관계를 보존한 검색 문장을 구성하고, 사용자가 원하는 정보에 따라
매뉴얼/SOP 또는 정비이력 검색 도구를 선택한다. 두 종류가 필요하면 각각 검색하며 고정된
검색 우선순위는 없다. 키워드 추출과 대상 선택은 기존 Claude 도구 루프 안에서 수행한다.
설비·모델·코드·기간은 선택 조건이다. 생략한 조건으로 검색 범위를 제한하지 않으며
모델이 ID·코드·날짜를 임의로 채우지 않는다. 넓은 질문도 관련 자료를 검색하고 여러 자료는
구분하여 안내한다. 빈 결과는 조건 입력 요구의 근거가 아니다.
지시 대상 부재·명시 조건 충돌·필수 적용 조건의 선택이 필요한 때만 추가로 확인한다.

`NEEDS_CLARIFICATION`의 `message`에는 확인이 필요한 구체적 이유를,
`clarification_questions`에는 사용자가 답해야 할 최소 질문을 반환한다. 고정 안내로
덮어쓰지 않으며 이유·질문은 별도 근거 검토 호출로 확인한다. 근거 없는 원인 단정·조치
지시·불필요한 필터 요구가 있으면 재작성한다(최대 2회 검토, 전체 시간 예산 공유).
근거 적용 조건 충돌도 모델에게 되돌려 어떤 조건의 선택이 필요한지 설명하게 한다.
`INSUFFICIENT_EVIDENCE`의 `message`도 고정하지 않고, 관련 자료 미발견과 조회 자료의
내용 부족을 구분하여 무엇을 확인하지 못했는지 설명한다. 실제 조회 조건·반환 개수·본문으로
설명을 검토하며 자료 전체에 기록이 없다고 과장하지 않는다. 설명 검토는 최대 2회다.
일부만 답할 수 있으면 `OK` 본문에 출처와 함께 확인된 내용 및 확인할 수 없는 부분을 구분한다.
답변 검토 2회 실패 시에는 자료가 없다는 안내 대신, 작성한 답변을 조회 근거로 확인하지
못했다는 서버 안내를 반환한다. 응답 계약·터미널 출력 형식은 바꾸지 않는다.
실제 Claude의 도구 선택·검토 정확성은 별도 E2E 확인이 필요하다.

실행은 최대 12턴(기본은 공용 설정), 검색 8회, 누적 근거 20개·본문 32000자로 제한한다.
자유 대화의 기간 목록은 집계 출처 1개를 위해 보고서 목록을 최대 19건으로 줄인다.
직접 DB 조회(`chat-check history`)는 계약의 limit 상한인 20건까지 반환할 수 있다.
검색 한 건 본문은 8000자 이하다. 요청의 timeout_s는 큐 대기·도구·모델 호출 전후 남은
시간을 확인하는 예산이다. 외부 구현도 해당 timeout_s를 지켜야 하며 실행 중 스레드를
강제 종료하는 기능은 아니다. 같은 서비스 객체 호출은 직렬화하고 전용 클라이언트를
주입해야 하며 다른 실행기와 하나의 가변 클라이언트를 동시에 공유하지 않는다.

답변의 출처는 이번 실행에서 도구가 반환한 것만 허용하고, 문서/사례/FAQ 종류와
출처 상태를 검증한다. 가상 여부는 서버 출처에 유지하며 답변 본문의 가상 문구는 강제하지 않는다.
존재하지 않는 인용은 모델에게 오류로 돌려 수정하게 한다.
제어·정비 작성·결재 도구는 없다. 본문 주장과 근거의 의미적 부합, 관련도 정책,
공급자별 오류 세분화·사용량·근거 대조는 #89에서 구현했다. 실제 API E2E는 사용자 키 준비 후 검증한다.

가짜 LLM·공통 검색기로 루프·검증을 검사한다.
`uv run --no-sync pytest tests/agent/test_chat_service.py tests/contracts/test_chat_tools.py`
실제 검색기는 SQLite 문서 레지스트리·공유 검색 구현과 저장소 4종(메모리/Qdrant 메모리·경로/Chroma)으로
검증한다. 외부 Claude 응답은 테스트에서 대체하며 유료 실API E2E는 자동 호출하지 않는다.
CLI는 로그인 사용자 서비스와 별개다. 인증된 HTTP는 [CHAT_API](CHAT_API.md)를 따른다.
보고서 원문 조회 API는 모든 로그인 사용자가 초안·반려·과거 버전을 열 수 있고
전체 목록은 `GET /reports?scope=all`을 제공한다. 기존 화면의 내 보고서 필터는 유지한다.

## 실제 검색 연결과 실행 (#88)

```bash
make index-reports         # 승인 보고서 색인 대기 작업 처리
make chat ARGS='"P03 매뉴얼과 정비 사례를 찾아줘" --asset-id BLDC-001'
make chat ARGS='"10월 승인 정비 보고서는 몇 건인가요?" --date-from 2026-10-01 --date-to 2026-10-31'
```

`make chat`은 .env의 기존 Claude 설정을 사용하며 **실제 API 비용이 발생**한다.
DB와 색인이 준비돼 있어야 한다. 최신 dev의 운영 문서는 자료 관리 화면에서 등록한다.
등록 과정에서 DB 저장·색인을 수행하며 기존 make index 자동 등록은 제거됐다.
CLI는 개발용 단일 질문 도구로 인증 HTTP API·대화 저장을
대신하지 않는다. FAQ 선택·채팅 시작 HTTP는 #91에 연결했고 화면은 #92에서 연결한다.

- 매뉴얼·SOP·룰 문서는 현재 completed·approved 레지스트리의 판과 파일 해시가 일치하는
  청크만 반환한다. 페이지/절이 없으면 추측하지 않고 제외한다. 개정·삭제·색인 지연을 검사한다.
- 설비·모델 필터는 문서 `extra.asset_id`/`extra.model`과 일치해야 한다. 웹 등록 시 실제 설비 ID를
  입력한다. 평가용 문서 3개의 extra.asset_id는 BLDC-001이다. 모델 이름은 자료에 없으므로 만들어 넣지 않았다.
  해당 값이 등록되지 않았으면 조용히 전체 검색하지 않고 확인 질문용 오류로 반환한다.
- 보고서 모델 필터와 매뉴얼 정비일 필터는 지원하지 않는다고 명시적으로 거부한다.
- 보고서는 DB의 최신 APPROVED 판을 선택하며 현재 작성 중인 개정판이 이를 가리지 않는다.
  원문 열람 정책과 독립적이다. 조건에 맞는 판이 아직 색인되지 않았으면 유사 검색에서
  이전 판을 대신 쓰지 않는다. DB 목록·집계는 색인 지연에 영향받지 않는다.
- 기간은 **Asia/Seoul 실제 조치일, 양 끝 포함**이다. 여러 조치 중 하나라도 범위에 들면
  보고서 1건으로 센다. 조치일 없는 보고서는 기간 조회에서 제외하고 사건일로 대체하지 않는다.
- 모델에게 전달하는 보고서 본문은 DB 사람 작성 칸으로 재구성한다. 설비·조치 시각은
  포함하고 사번·AI 분석·결재는 제외한다. SYNTHETIC 값은 서버 출처에 유지하며 본문 표시는 강제하지 않는다.
- 모든 조회는 공통 열람으로 직책 ACL을 추가하지 않는다. 로그인과 대화 소유권은
  HTTP API에서 검사한다. 검색·DB 자체 실패는 빈 결과로 숨기지 않는다.
- 현재 승인 판 전체를 DB에서 읽어 Python으로 기간 조건·집계를 계산한다. 대량 운영 시
  SQL 투영·집계 최적화가 필요하다. 전체 예산은 호출 전후 검사하며 로컬 모델의 실행 중
  강제 취소는 지원하지 않는다. 응답 출처 ID를 실제 원문 링크로 표시하는 화면은 #92 범위다.

## Claude 없이 기능별 확인

`make chat-check`는 자연어 도구 선택·답변 생성을 생략하고 각 기능을 직접 실행한다.
Claude API를 호출하지 않으며 FAQ 외의 명령은 DB 연결이 필요하다.

```bash
make chat-check ARGS='faq'
make chat-check ARGS='faq --faq-id FAQ-ACCESS-001'
make chat-check ARGS='search "P03 입구 센서 점검 절차" --asset-id BLDC-001 --code BTT2-P03 --limit 3'
make chat-check ARGS='search "센서 청소 사례" --kind MAINTENANCE_HISTORY --asset-id BLDC-001'
make chat-check ARGS='history --asset-id BLDC-001 --date-from 2026-10-01 --date-to 2026-10-31'
```

`search`는 관련 본문·출처 목록, `history`는 전체 승인 보고서 수·가상 보고서 수·제한된
목록을 JSON으로 출력한다. 승인된 보고서를 아직 등록하지 않았다면 이력은 0건이 정상이다.
검색어는 임의 문장으로 입력할 수 있지만 설비·코드·기간은 옵션으로 직접 지정해야 한다.
로컬 Qdrant 경로를 여는 다른 프로세스와는 동시에 실행하지 않는다.

## 자연어 질문에서 검색까지

사용자가 질문하면 `ToolChatService`가 기준 날짜·시간대·사용자 선택 조건과 함께
Claude에 전달한다. Claude가 검색 문장과 자료 종류, 설비·코드·기간을 도구 입력으로
추출한다. 별도 사전 분류 모델은 없다. 자연어 해석 자체가 항상 정확하다는 보장은 없으며,
서버는 추출된 조건의 형식·실제 지원 여부와 사용자 명시 조건 보존을 검증한다.

관련 내용을 찾는 질문은 `search_knowledge`로 처리한다. `DatabaseChatKnowledge`가
DB에서 현재 문서 판·최신 승인 보고서와 조건을 확인한 뒤 공유 검색기에 대상 ID·판을
전달한다. 검색기는 의미 벡터 검색과 BM25 키워드 검색을 RRF로 결합하고, 설정된 경우
리랭커로 후보를 재정렬한다. 검증된 본문·출처를 받은 Claude가 답변을 제출하면 서버가
인용 ID·출처 상태를 다시 확인한다. 가상 여부는 출처에 보존하며 본문에 반복할 필요는 없다.
매뉴얼과 정비 사례가 모두 필요하면 두 종류의 도구 검색 결과를 모아 답변할 수 있다.

기간 목록·정확한 건수는 `query_history`가 DB의 전체 대상에서 계산한다. 이 경로는
자연어의 임의 의미 조건을 모두 지원하는 조회가 아니라 설비·코드·실제 조치일 조건의
승인 보고서 조회다. 예를 들어 '특정 부품을 교체한 전체 건수'를 텍스트 유사 검색 결과
개수로 대신 계산할 수 없다.

### 과거 정비이력과 과거 개정판의 차이

| 요청 | 현재 지원 범위 |
|---|---|
| 지난달·작년의 정비 보고서 검색 | 저장된 보고서별 최신 승인 판의 실제 조치일로 필터링. 오래된 보고서도 대상 |
| 해당 기간의 승인 보고서 목록·건수 | DB 구조화 조회. 목록 길이 제한과 전체 건수는 구분 |
| 같은 보고서의 이전 개정판 원문 조회 | 기존 인증 API `GET /reports/{report_id}/versions/{version}`에서 지원 |
| 챗봇에서 보고서의 특정 이전 개정판 검색 | 미지원. 검색에는 보고서별 최신 승인 판만 사용 |
| 챗봇에서 매뉴얼 구버전 검색·신구 비교 | 미지원. 현재 레지스트리 판만 검색하며 색인은 같은 문서 ID의 이전 판을 교체 |
| 특정 과거 시점에 유효했던 문서·보고서 상태 재현 | 미지원. 기간 조건은 정비 조치일이며 당시 문서 효력·승인 시점을 뜻하지 않음 |

구버전 검색을 지원하려면 문서별 여러 버전의 보관·색인, 버전/기준 시점 선택 계약,
과거 판임을 명시하는 답변 정책을 별도로 추가해야 한다. 원문 열람이 허용된다는 사실이
그 판을 현재 챗봇 검색에 포함한다는 뜻은 아니다.

## #89 답변 검증·직접 대화

`agent/chat_grounding.py`는 최종 OK 답변의 부분별 주장과 실제 인용 본문을 별도 구조화
Claude 호출로 대조한다. 새 분류기나 자율 도구 에이전트는 아니며 기존 클라이언트로
검토만 수행한다. 근거 없는 단정·수치·조치 일반화는 수정 요청으로 돌려주고 최대 두 번의
검토 후에도 뒷받침되지 않으면 INSUFFICIENT_EVIDENCE로 멈춘다. 적용 조건을 섞은 충돌은
NEEDS_CLARIFICATION이다. 검토 JSON 오류·서비스 장애는 정상 답변으로 통과시키지 않는다.
같은 모델 응답에 제출 도구가 여러 개여도 첫 유효 제출에서 실행을 끝낸다.
NEEDS_CLARIFICATION은 이유와 구체적인 질문을 별도로 검토한 뒤 그대로 전달한다.
근거 없는 단정·조치 지시·불필요한 선택 조건 요구는 사용자에게 표시하지 않는다.
OK 검토 후에도 출처 삭제/개정을 다시 검사한다. OK·OUT_OF_SCOPE의 안내 message는 서버 문구를 쓴다.
검토 모델도 오판할 수 있으므로 이 장치는 사실성의 완전한 보장이나 전문가 판단을 대신하지 않는다.

`_BudgetClient`는 같은 요청의 대화·근거 검토 호출을 함께 집계하고 실제 tracer를
run_agent에 전달한다. `ToolChatService.last_run`은 request_id·호출별 공급자/실제 모델·
토큰·시간·실패 여부와 도구 이름만 보관한다. 질문·답변·키는 이 통계에 저장하지 않는다.
사용량이 없는 호출은 None이며 합계도 미확인이다. 재시도 이전 시도의 과금은 확인할 수
없어 최종 응답 토큰이 있더라도 합계는 미확인으로 표시하고 통신 시도 수를 별도로 남긴다. 공통 런타임 trace도 이를 0으로 확정하지 않는다.
요청이 겹치는 외부 API에서는 request_id에 맞는 통계만 사용해야 한다.

Claude 클라이언트는 인증/권한 오류, 429, 네트워크/5xx, 시간 초과, 잘못된 응답을
구분한다. 429·네트워크·시간 초과·5xx에만 같은 호출 예산 안에서 최대 두 번 재시도한다.
SDK의 내부 중복 재시도는 끈다. 인증·잘못된 입력은 즉시 실패한다. 각 시도는 남은 시간과
0.25/0.5초 대기를 사용한다. 네트워크 장애 뒤 실제 과금 여부는 알 수 없으며 사용량을
추정해서 0으로 기록하지 않는다. 원시 예외 본문을 화면·추적 오류 메시지에 남기지 않는다.

### API 키를 추가한 뒤 사용자 터미널에서 실행

1. Docker Desktop을 켜고 `make db-up`으로 PostgreSQL을 실행한다.
2. 웹 자료 관리 화면에서 문서 등록/색인을 완료한다. 기존에 완료한 색인은 재사용한다.
3. 로컬 Qdrant를 여는 다른 API/CLI 프로세스를 종료한다.
4. 프로젝트 루트의 **사용자 터미널**에서 아래 명령을 실행한다. 키는 채팅창에 보내지 않는다.

```bash
make chat-private ARGS='--asset-id BLDC-001'
```

키 프롬프트에서 입력해도 화면에 표시되지 않는다. 키는 해당 Python 프로세스의 SDK에
전달하고 파일·argv·환경변수에는 저장하지 않는다. 명령은 .env를 자동 로드하지 않으므로
별도 설정이 없다면 기본 PostgreSQL·로컬 Qdrant·모델 설정을 사용한다. DB나 모델 설정이
기본과 다르면 본인 터미널에서 필요한 설정을 별도로 제공해야 한다.
`make chat`은 기존 호환 경로로 .env를 로드하므로 비밀 파일을 남기지 않으려면 private 명령을 쓴다.

```text
Claude API 키 (화면 표시·파일 저장 없음):
나: P03 발생 시 무엇부터 확인해야 해?
챗봇 [OK]: ...답변과 출처...
나: 매뉴얼 근거를 더 구체적으로 알려줘
나: /reset
나: 지난달 승인 정비 보고서는 몇 건이야?
나: /exit
```

이전 대화는 메모리에만 최대 20개 메시지·16000자로 유지한다. /reset은 이전 문맥을
지우고 /exit 또는 Ctrl+C는 종료한다. 명시한 설비·기간 옵션은 같은 실행 동안 유지되므로
다른 고정 조건으로 바꾸려면 종료 후 다시 실행한다. 매 턴 실제 API 비용이 발생하며
근거 검토 호출도 포함한다. 첫 임베딩·리랭커 로드는 시간이 걸릴 수 있다.
기본 출력은 답변·출처이며 호출 수·토큰·시간·도구 목록은 숨긴다. 진단이 필요하면
`--stats`를 지정하면 stderr에 표시한다(예: `make chat-private ARGS='--stats'`).
대표 질문은 매뉴얼 절차, 기간별 건수, 없는 자료, 조건이 모호한 질문, 재가동 요청을
차례로 넣어 도구·상태·출처를 확인한다. 보고서가 없으면 승인 보고서 0건이 정상이다.

단일 질문 JSON과 사용량을 확인하려면(키 숨김 입력, .env 미로딩):

```bash
PYTHONPATH=src uv run --no-sync --no-env-file python scripts/chat.py --ask-key --stats "P03 점검 절차는?" --asset-id BLDC-001
```

키 없이 실행 가능한 자동 검증은 `make check`, FAQ·실제 검색·DB 조회는 기존
`make chat-check`다. 이 구현 과정에서는 실제 Claude API·비밀 파일을 사용하지 않았다.
실제 키의 유효성·모델 사용 권한·대표 질문 E2E는 키를 준비한 사용자가 마지막으로 확인한다.

### AI 에이전트가 키를 보지 않게 하는 범위

- AGENTS.md·CLAUDE.md에 실제 .env/인증 프로필 읽기·환경 덤프·실API 실행 금지를 기록했다.
  이는 앞으로의 행동 지침이며 OS 차단은 아니다.
- gitignore는 커밋 제외 기능이다. 에이전트의 읽기를 차단하지 않는다. 저장소 밖 파일,
  같은 계정의 Keychain·컨테이너·별도 터미널도 접근 권한을 공유하면 절대 차단을 보장하지 못한다.
- 숨김 입력은 키의 파일·터미널 기록 노출을 줄이지만 SDK가 쓰는 동안 프로세스 메모리에는 존재한다.
  같은 OS 계정의 프로세스/메모리 접근까지 허용된 환경에서는 절대 접근 불가를 보장할 수 없다.
- 강한 격리가 필요하면 키를 별도 OS 사용자 또는 별도 서버의 신뢰된 실행 환경에 두고,
  에이전트에는 그 환경의 파일·프로세스·SSH·Docker 관리 권한을 주지 않는다. 가능하면
  신뢰된 서버가 키를 소유한 채 제한된 API만 제공하고 작업 환경에는 키를 전달하지 않는다.
  에이전트가 수정한 코드에 키를 넣어 실행하기 전에는 사용자 검토도 필요하다.
- 키를 채팅·스크린샷·소스·명령 인자에 붙여 넣지 않는다. Langfuse 본문 캡처는 기본 false를
  유지한다. API 키를 질문 본문으로 입력하지 않는다.

## HTTP API (#91)

`api/chat.py`를 기존 FastAPI 앱에 연결했다. 기존 Bearer 로그인으로 인증하고 세션 사번을
사용해 대화 소유권·중복 요청을 검증한다. FAQ 버튼 선택과 자유 질문 전송 경로를 분리한다.
대화 생성·목록·조회·갱신·삭제와 요청 상태 조회를 제공한다.
202는 처리 중, 200은 응답 저장 완료이며 응답 자체의 status도 별도로 확인한다.
타인 대화/없는 대화는 동일 404, 요청 충돌/결과 불명은 409다.
실행 전 실패만 retry_allowed를 확인해 명시적 재시도한다.
경로·JSON 예시·오류 매핑·Swagger 실행법은 [CHAT_API](CHAT_API.md)를 따른다.

## 실행·제한 정책 제안 (#89·#91, 미구현)

공용 LLM은 #101/#107에서 Claude로 전환됐다. `get_llm_client()`와 기존
`LlmClient.create()`를 자유 대화 도구 루프에 재사용하며 별도 공급자 어댑터를 만들지 않는다.
현재 출력 상한은 공용 Claude 구현의 16000토큰이고 타임아웃·재시도는 SDK 설정을 따른다.
아래 1024토큰·전체 시간 예산은 챗봇의 후속 제안이며 현재 구현된 제한으로 간주하지 않는다.
현재 인증/연결 실패는 같은 `LlmUnavailableError`, 429/5xx는 일반 `LlmError`로 전달된다.
세부 오류 매핑·전체 시간 예산·재시도 정책은 #89에서 공용 클라이언트와 함께 보완한다.

- API 수명주기에서 검색 모델·저장소·공급자 HTTP 클라이언트를 만들고 재사용한다.
- 동기 ChatService와 검색·임베딩·LLM은 제한된 작업 스레드에서 실행해 이벤트 루프를
  막지 않는다. 스레드 대기를 취소해도 내부 호출이 멈추는 것은 아니므로 HTTP 타임아웃과
  단계별 남은 시간 확인을 함께 구현한다. 같은 DB 세션을 스레드 간 공유하지 않는다.
- 전체 처리 60초, 검색 10초, LLM은 남은 시간 이내, 연결 5초를 초기 제안으로 둔다.
  전체 예산은 큐 대기·재시도·대기를 포함한다. 출력 1024토큰, 서버 동시 생성 2개,
  재시도 최대 1회로 시작하되 #89·#91 구현·평가에서 설정값을 확정한다.
- 타임아웃·429·일시 장애만 남은 예산 내에서 제한적으로 재시도한다. 인증·잘못된 요청은
  자동 재시도하지 않는다. 서비스 장애를 근거 부족으로 숨기거나 로컬 LLM으로 우회하지 않는다.
- 계약 상한: 질문 2000자, 최근 대화 20개·각 4000자·총 16000자, 검색 20개.
  토큰 한도는 별도로 구현하며 최근 대화만 공급자에 보낸다.
- 대화 저장 요청·응답에는 사용량 필드를 두지 않고 #90에서 별도로 영구 저장하지 않는다.
  기존 #89의 공급자·모델·입출력 토큰·지연·시도 수 수집과 누락/재시도 사용량의
  미확인 표시는 유지한다. 요청마다 전용 서비스를 만들며 키·전체 프롬프트·개인정보는
  로그에 남기지 않는다. FAQ 직접 응답은 LLM을 호출하지 않는다.

## 현재 주의·경고와 회복 사건

자유 질문에서 Claude가 `query_incidents`를 선택하면 PostgreSQL의 사건을 직접 조회한다.
매뉴얼·보고서 벡터 검색은 이 조회에 사용하지 않는다. `ANALYSIS_AUTO_ENABLED=true`로
센서를 수신해 사건이 DB에 저장되어 있어야 한다. 기존 DB 기록도 조회할 수 있다.

- “지금 주의와 경고 현황 요약해줘”: 전체 등급별 건수와 제한된 설비·코드·발생 시각 목록.
- “이 주의 알림은 왜 발생했어?”: 사건의 측정값과 판정 기준·관측 설명. 실제 고장 원인은 확정하지 않는다.
- “아까 사라진 경고는 뭐였어?”: 조건에 맞는 가장 최근 회복 사건 한 건과 회복 시각.
  다른 알림을 의도했다면 발생/회복 시간대를 알려 달라는 안내를 서버가 덧붙인다.
- “오늘 14시부터 15시 사이 회복된 경고”: 해당 회복 시간 범위로 조회하며 없으면 0건으로 안내한다.

새로운 INCIDENT 본문과 INCIDENT_QUERY 출처는 기존 개인 대화 저장·HTTP·웹 UI·CLI를 통과한다.
측정값이나 판정 기준이 기록되지 않았으면 누락을 밝힌다. 매뉴얼 기준을 당시 측정값으로 만들지 않는다.
집계는 조회 시점 DB 기준이며 실시간 수신 상태를 보장하지 않는다. 마지막 이상 감지·회복 시각을 구분한다.

Claude API 키 없이 사건 저장/조회만 확인:

```bash
make chat-check ARGS='incidents'
make chat-check ARGS='incidents --severity Warning --asset-id BLDC-001'
make chat-check ARGS='incidents --state RECOVERED --severity Error'
make chat-check ARGS='incidents --state RECOVERED --time-from 2026-11-02T14:00:00+09:00 --time-to 2026-11-02T15:00:00+09:00'
```

화면에서 직접 대화하려면 API·프론트엔드를 재시작한 뒤 기존 채팅 시작 버튼을 사용한다.
터미널 대화는 `make chat-private ARGS='--asset-id BLDC-001'`로 실행할 수 있다(Claude 비용 발생).
